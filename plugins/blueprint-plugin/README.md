# Blueprint

Локальный плагин Codex для интерактивного планирования: MDX, вопросы, custom React-компоненты, аннотации, история и обсуждения между оператором и агентом.

## Разработка

Требуется Bun 1.4.2. `bun install --frozen-lockfile`, `bun run build`, `bun test`, `bun run typecheck`. Команда сборки создаёт `dist/blueprint-plugin/`, включая `bin/blueprint` с Bun runtime и встроенным интерфейсом. У конечного пользователя Node/Bun не требуются. Артефакт предназначен для ОС и архитектуры машины сборки.

`dist/blueprint-plugin/bin/blueprint serve /absolute/project` запускает сервер в foreground и выводит локальную ссылку. Ctrl+C останавливает сервер и освобождает блокировку. Ссылка содержит секрет доступа: не коммитьте и не публикуйте её.

Для Codex установите собранный каталог как локальный плагин поддерживаемым вашей версией приложения способом. `.mcp.json` запускает `${PLUGIN_ROOT}/bin/blueprint mcp`. Рабочий каталог MCP должен быть пользовательским проектом. MCP transport smoke-test не является доказательством установки в Desktop; см. результаты проверки в `VALIDATION.md`.

## Данные

`blueprints/<name>/blueprint.mdx` и каталоги `widgets/`, `assets/` — рабочие исходники. `metadata.json` хранит редакции, состояния виджетов и курсоры читателей. `annotations.json` хранит обсуждения с авторами, ответами и историей. `revisions/<n>.json` — неизменяемый snapshot исходников и bundle; `changes/<cursor>.json` — последовательный журнал изменений. Схема v2. Старые `submissions/` сохраняются как исторические файлы, новые пакеты больше не создаются. При первом открытии v1 сохраняется `migration-v1.json` с исходными метаданными и аннотациями, затем выполняется атомарная миграция. Не открывайте обновлённое хранилище старым бинарником. Git-включение данных решает пользователь.

Запись проходит через атомарную замену и журнал `.transaction.json`. После сбоя следующая операция завершает подготовленную транзакцию. Неполный журнал не игнорируется. `.blueprint.lock` запрещает двух писателей. После аварийного завершения проверьте записанный PID и отсутствие владельца, затем удалите только устаревший lock. Симлинки внутри хранилища запрещены.

## Взаимодействие

Пользователь явно переключает редакции. Аннотации сохраняют исходную редакцию и цитату; комментарии другой редакции показываются как требующие проверки. Автоматического угадывания новой привязки нет. Сравнение показывает исходный и текущий MDX.

Ответы сохраняются без модели. Оператор сохраняет аннотации и пишет агенту в чат, когда нужно продолжить; отдельной отправки нет. Черновик явно сохраняется кнопкой **Save draft** и открывается в работу через **Open for review**. Несохранённый текст формы ещё не является записью артефакта. Агент перечитывает текущее состояние, историю изменений и отвечает в обсуждениях. **Approve revision** фиксирует редакцию и состояние, не запускает реализацию.

Аннотации: `draft → open → in_progress → ready_for_review → resolved`; `needs_input` обозначает запрос уточнения. Агент переводит открытое обсуждение в работу или запрос уточнения, отвечает и предлагает результат для проверки. Оператор один принимает результат, возвращает обсуждение в `open`, архивирует и восстанавливает. Архивирование — отдельное свойство. Исходный текст редактирует только его автор, история правок и ответы сохраняются. Предложение агента — аннотация или ответ с авторством, а не замена ответа оператора. Смена редакции не закрывает обсуждение; привязка к другой редакции явно требует проверки.

MCP: `open_blueprint`, `read_blueprint`, `describe_widget`, `publish_revision`, `read_changes`, `wait_for_changes`, `acknowledge_changes`, `add_annotation`, `update_annotation`. Для публикации нужны `expectedRevision` и `expectedEvent`, для изменения обсуждения — `expectedVersion` и idempotency ID операции. Роль задаётся сервером: HTTP — оператор, MCP — агент. MCP не предоставляет запись ответов оператора, разрешение или архивирование аннотаций.

`read_changes` отдаёт до 50 позиций журнала и `cursor/hasMore`; текст черновиков скрыт. Отдельный `reader` хранит курсор каждой задачи. Чтение не означает обработку: `acknowledge_changes` выполняется после неё, с ожидаемым прежним курсором. После миграции журнал начинается с события миграции; более раннее состояние доступно в сохранённых файлах, но не реконструируется в события. `wait_for_changes` — необязательное ограниченное ожидание внутри активного хода; автоматического запуска нового хода нет.

Blueprint — доверенный исполняемый код локального проекта. Полный MDX и custom React исполняются в общем DOM страницы без iframe; это делает текст и виджеты доступными нативному аннотатору браузера. Код документа имеет полномочия интерфейса, включая доступ к локальному API. Сборка остаётся в отдельном процессе, импорты ограничены локальными исходниками и поставляемыми библиотеками. HTTP API сохраняет проверку токена, Origin/Host и входных данных. Error Boundary показывает ошибки React; бесконечный цикл JavaScript может заблокировать страницу.

Переключатель **Blueprint annotator** отключает создание аннотаций через выделение; существующие обсуждения остаются доступны. Предпочтение сохраняется в браузере для текущего origin (не в профиле MCP-харнесса). Комментарии нативного аннотатора поступают в чат; автоматического импорта в историю Blueprint нет.

Компилятор ограничен таймаутом 20 секунд, количество файлов — 100, размер исходников — 4 MB; сообщения UI — 128 KB, подписчики ядра — 64, SSE — 16. История хранится на диске и растёт по числу редакций; безлимитные серверные кэши не используются.

Будущий режим фонового сервиса может переиспользовать ядро/HTTP. Автоустановка LaunchAgent, автоматический запуск idle-задачи и MCP Apps не входят в v1.

## GitHub Actions и ZIP

Workflow `.github/workflows/build.yml` запускается на push, pull request и вручную через **Actions → Build plugin → Run workflow**. Runner `macos-15` проверяет ARM64; Bun закреплён на 1.4.2, зависимости устанавливаются с `--frozen-lockfile`. Сначала собирается executable и встроенный frontend, затем выполняются TypeScript, unit/integration tests и браузерная проверка на Chromium из Playwright.

`bun run package` упаковывает уже собранный каталог в `dist/blueprint-plugin-macos-arm64.zip`: `.codex-plugin/plugin.json` лежит в корне, права executable сохраняются. Упаковщик проверяет ZIP, извлекает его системным `unzip` и выполняет MCP/HTTP smoke-test именно извлечённого бинарника с изолированными PATH и HOME. Для упаковки на машине разработчика требуется Python 3.9+; в устанавливаемый плагин Python не входит. Рядом создаётся SHA256-файл.

В успешном запуске GitHub скачайте `blueprint-plugin-macos-arm64.zip` из **Artifacts** и загрузите его в штатный интерфейс установки Codex. ZIP загружается через `upload-artifact` с `archive: false`, без дополнительного внешнего ZIP. Срок хранения — 14 дней. Размер и SHA256 записываются в summary запуска. Workflow не создаёт GitHub Release и не требует секретов.

Локально: `bun install --frozen-lockfile`, `bun run build`, `bun run typecheck`, `bun test`, `bun run check:browser`, `bun run package`. Браузерная проверка использует установленный Chrome; путь можно задать через `BLUEPRINT_BROWSER_EXECUTABLE`. В CI используется Chromium, установленный командой `bunx --no-install playwright install chromium`.

Установка ZIP через штатный интерфейс подтверждена пользователем. Системный сервис пока не нужен: возвращаемся к нему только при выявленной нехватке MCP-процесса.

## Релизы и версии

Версия меняется только в релизном workflow `.github/workflows/release.yml`. Обычные сборки сохраняют текущую версию; используем `0.1.*`. Источник версии — `package.json`; MCP и CLI импортируют её, manifest плагина синхронизируется релизным скриптом. Сборка проверяет отсутствие расхождений.

В GitHub Actions выберите **Release plugin → Run workflow**, основную ветку и новую версию без префикса `v`, например `0.1.3`. Запуск из другой ветки пропускается. Workflow выполняет проверки исходников, создаёт локальный коммит только двух файлов версии, собирает executable и ZIP и проверяет извлечённый пакет. Лишь после этого атомарно отправляет коммит и тег `v0.1.3`, загружает ZIP и SHA256 в черновик GitHub Release, скачивает их для проверки и публикует Release.

Если основная ветка изменилась во время проверок, публикация останавливается без перезаписи чужих изменений. Запустите workflow заново на новой вершине ветки. Выполняется один релизный запуск одновременно; активный запуск не отменяется новым.

При сбое после отправки тега повторите запуск с **той же версией**: workflow использует существующий release-коммит, повторяет проверки и завершает публикацию черновика. Новый коммит и версия не создаются. Уже опубликованный релиз остаётся неизменным. Пока release остаётся черновиком, его артефакты могут быть заменены проверенной повторной сборкой того же коммита.

Используется встроенный `GITHUB_TOKEN` с `contents: write`, отдельный PAT не нужен. Правила защиты основной ветки должны разрешать предусмотренный release-коммит; workflow не обходит branch protection. Если прямой push запрещён, потребуется отдельно согласованный процесс через release PR. Отправка refs и публикация Release не атомарны между собой: после сетевой ошибки тег может уже существовать, а Release ещё требовать повторного запуска.

GitHub Release workflow пока проверен только локально: до первого hosted-запуска требуется GitHub-репозиторий с этими файлами. Обновление marketplace в этот workflow не входит.
